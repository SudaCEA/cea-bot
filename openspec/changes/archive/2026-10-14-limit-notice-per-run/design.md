# Design: limit-notice-per-run

## Context

- 现行行为：`handlers/notice.py` 的 `_run_locked` 直接遍历 `schema.plan_run(...).pending`
  全量投递；待推送集合按 `published_on DESC, edit_id DESC` 排序（`schema.pending`）。
- 记账语义（design.md D7，上一变更）：**先发送成功、再 `claim_and_mark`**，
  未记账的条目下次仍在 `pending` 里 —— 这正是"留待下次继续投"能落地的机制，无需新机制。
- 既有同类键 `notice_max_chars`（缺省 1500，**必须为正整数**，0 视为"把正文截空"而拒绝）。
- 配置项必须落进 `check_config` 的返回值：下游只拿得到校验后的字典，漏掉就是死键
  （上一变更的审查 B 抓到过这个高severity 缺陷）。

## Goals / Non-Goals

**Goals:**

- 单次检查的投递条数可控，且**不丢条目**（超出上限的留到下次）
- 上限的取舍在日志与规格里都可观察、可断言
- 默认不改变既有行为（缺省 = 不限制）

**Non-Goals:**

- 不引入"按时间窗口限流"（如每小时最多 N 条）—— 定点本身已是时间栅格
- 不引入优先级/按栏目配额
- 不改动增量状态表结构（不需要新列：`pushed_at IS NULL` 天然表达"还没推"）
- 不改动 `notice_max_chars` 的语义（它仍是"必须正整数"）

## Decisions

**D1. 键名 `notice_max_per_run`，缺省 `0` = 不限制。**
缺省不限制是为了让这次改动**不改变既有部署的行为**（想限额的人显式配置）。
取值须为非负整数；负数或非整数 → 配置期 `sys.exit` 并给出可执行提示。
备选：缺省给一个正数（如 3）——但那会让"没配过这个键"的部署行为突变，且数字没有客观依据。

**D2. 上限统计的是"成功投递条数"，不是"处理条数"。**
失败的条目不计入上限名额（仍记 `last_error`、下轮重试）。理由是避免饥饿：
若按处理条数计，一个**持续失败的最新条目**（例如详情页坏了）会每次都占掉名额，
把更旧的条目永远挤在后面。规格措辞用的是"投递"，与这里的口径一致。
代价：一轮里实际"处理"的条目数**不受上限约束**，其上界是本轮 `pending` 的长度 ——
而 `schema.pending()` 取的是**整表** `pushed_at IS NULL`（并不限于列表首页的 20 条），
所以积压量会随失败轮次累积（独立审查复核：积压 60 条且详情全失败时，本轮就会发 60 次详情请求；
持续失败且每轮新增 5 条时，单轮处理量 5 → 10 → 15 递增）。
取舍：这是"不饿死旧条目"的必然代价，请求量随积压**线性**增长而非无界发散，且单条失败不拖垮整轮；
要给"单轮处理量"一个硬上界就必须改规格（会与"失败不占用上限名额"直接冲突），故不在本变更内做，
留待后续 change 评估。

**D3. 取新不取旧：超出上限的留在 `pending`，下次定点继续。**
`pending` 已按发布时间倒序，故"先推最近的"是自然结果，也正是用户想要的（最新的通知最要紧）。
实现上**不需要任何新状态**：不调用 `claim_and_mark` 就等于"下次再来"。
日志必须报数：`本次投递 N 条（上限 M），剩余 K 条待下次定点`。

**D4. 干跑套用同一上限与同一计划。**
干跑的定义是"照常抓取/摘要/渲染，只是不发送"；若干跑不受上限约束，它就无法用来预演真实行为。
`pushed` 的记账在干跑下也会发生（既有行为），故剩余条数的口径与真实运行一致。

**D5. 与首跑基线无交互。**
首跑只登记并标记基线、不投递任何条目（既有 D8），上限不参与该分支。

**D6. `RunResult` 增加 `remaining: int = 0`。**
口径：`remaining = len(plan.pending) - len(pushed)`，即"本轮结束后**仍未投递**的待推送条数"，
**含**本轮处理失败的条目（它们仍是 `pushed_at IS NULL`，下个定点重试）。
它**仅在 `skipped=False` 时有意义**：本轮被跳过时不产生计划，`remaining` 保持 `0`（表示"未计算"，
不等于"没有积压"）。让"还剩多少条"成为可断言的数据（而不是只能从日志里 grep），也便于将来接监控。
不改 `pushed`/`failed`/`baseline`/`skipped` 的既有语义。

**D7. 文档必须写清两个键的相反语义。**
`notice_max_chars`：必须正整数（0 = 把正文截空，拒绝）。`notice_max_per_run`：0 = 不限制。
两行挨着放在 README 配置表里并各带一句说明，避免"照着隔壁那行的直觉填 0"。

## Risks / Trade-offs

- [上限设得过小（如 1）导致积压条目前要很多个定点才推完]
  → 日志报剩余条数；README 给出建议（例如 3～5）与"积压多久能推完"的心算方式
- ["0 = 不限制"被误当成"一条都不推"]
  → 配置期不做反向猜测：0 明确等于不限制，并在 `config.example.yaml`、README、错误提示三处写明；
  真正的"一条都不推"应通过清空 `notice_targets`（关闭功能）实现
- [按成功计数会让一轮处理量超出上限]
  → 已在 D2 说明：单轮处理量不受上限约束、随积压线性增长（**不是**"不会发散"）；
  测试用"多条失败 + 上限 1"钉住"失败不占名额"，另有一条钉住"上限没截断时不得打印上限日志"
- [`remaining` 含失败条目，可能与失败日志里的剩余数被读成两个数]
  → 已定口径（D6）并把日志文案写成"剩余待投递 K 条（含本轮失败 N 条）"，避免同一批条目被报两次
- [上限与干跑/失败重试交互写错]
  → 用测试覆盖：`cap=1` 只推 1 条且其余仍 `pending`；`cap=1` 且最新一条失败时，本轮仍会投递下一条
