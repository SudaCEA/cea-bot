## 1. 解析层日期仍接受非 ASCII 数字（全角日期原样落库）

**状态**：待处理 —— 拟由变更 `normalize-notice-date-digits` 接手（2026-10-18 提出）。
**触发条件**：站点列表页给出全角数字的发布日期（如 `２０２６-１０-０１`）。

### 现状：三层口径不一致

| 层 | 位置 | 对 `２０２６-１０-０１` 的反应 |
|---|---|---|
| 解析 | `src/cea_bot/notices/parse.py:197` `_DATE = r"\d{4}-\d{2}-\d{2}"` | **认** —— Python 在 `str` 模式下 `\d` 匹配 Unicode `Nd` 类（含全角数字），命中原样返回 |
| 落库与排序 | `src/cea_bot/notices/schema.py:127` `ORDER BY published_on DESC` | SQLite 按 TEXT 二进制比较：全角数字的 UTF-8 首字节 `0xEF` > ASCII `2` 的 `0x32`，故全角日期**排到队首** |
| 产物命名 | `src/cea_bot/notices/pdf.py:52` `_ISO_DATE` 只认 `[0-9]` | **不认** → 回落固定占位 `000000` |

### 影响

1. 一条**最旧**的通知会抢走 `notice_max_per_run` 的名额，而规格要求"仅投递**最近的**若干条"；
2. 推送文本与摘要里显示全角日期，PDF 名却是 `000000-<标题>.pdf`，两边口径不一致；
3. `src/cea_bot/handlers/notice.py:259` 的 `missing_dates` 只统计**空串**，所以这类条目
   **一条告警都不会有** —— 是静默失效，不是"看起来正常"。

### 为何当时未做

`2026-10-14-rename-notice-pdf-with-title` 的 Impact 与 delta 只覆盖**命名**，动解析层的日期识别
属另一处行为；且三天真实抓取（10-12 / 10-13 / 10-14，共 34 条）**一次都没出现**全角日期。
原始记录见 `openspec/changes/archive/2026-10-14-rename-notice-pdf-with-title/tasks.md:111`。

### 实测取证（2026-10-18，只读探针 `.local/probe_date_forms.py`）

三个栏目首页共 **60 条**：`published_on` 全部是 ASCII；页面里非 ASCII 的 `Nd` 字符数为 **0**；
全角/异体连字符数为 **0**。也就是说**触发条件至今没在真实数据里出现过** ——
这条属**预防性修复**，不是线上故障。做与不做取决于"以后要不要为一次没发生过的页面改版买单"。

### 打算怎么改（口径已定：归一化 + 告警）

解析层对外只产出**唯一规范形式** ASCII `YYYY-MM-DD`；发生归一化时记一条日志（不静默）。
需一并考虑全角连字符 `－`（U+FF0D），以及 `\d` 还匹配的其它 Unicode 数字族（阿拉伯-印度数字等）。
规格目前**没有**任何条款钉住解析层的日期格式（`YYYY-MM-DD` 只出现在 PDF 命名那条 Requirement），
所以要为它补一条需求，而不是"顺手改实现"。

## 2. 默认运行路径仍在仓库内的相对目录（`data/`）

**状态**：待处理，未开工 —— 等"无修改直接部署"的需求真正铺开时再做。

### 现状

默认值是**相对路径** `data/state/cea_bot.db` 与 `data/notices`，以**进程 cwd** 为基准
（`start.sh` / `start.bat` 会先切到仓库根，故实际等于仓库根下的 `data/`）。
同一个字面量散在**四处代码 + 两处文档**：

| 位置 | 内容 |
|---|---|
| `src/cea_bot/config.py:31` | `_DEFAULT_NOTICE_DB_PATH` / `_DEFAULT_NOTICE_PDF_DIR`（校验时填进返回字典） |
| `src/cea_bot/handlers/notice.py:37` | `DEFAULT_DB_PATH` / `DEFAULT_PDF_DIR`（第二份字面量） |
| `src/cea_bot/__main__.py:32` | 启动期状态库校验里的第三份字面量 |
| `src/cea_bot/store.py:32` | `STATE_REMEDY` 硬编码"删除 data/state/cea_bot.db 后重建"，**未按实际配置路径插值** |
| `config.example.yaml:40` / `config.example.yaml:44` | 模板默认值 |
| `README.md:243` | 文档里的默认值表格（README §8 另有一段叮嘱"必须改成绝对路径"） |

`src/` 内**没有任何** `expanduser` / `Path.home()`：今天即便在配置里写 `~/cea` 也不会被展开。

### 打算怎么改

默认值收敛到**一处**来源，改为按平台的用户目录（Linux：`$XDG_DATA_HOME`，否则
`~/.local/share/cea-bot`；Windows：`%LOCALAPPDATA%\cea-bot`），并同步模板与 README §5/§8。
三个难点，都不是"改个字符串"能了事的：

1. **迁移是静默的** —— 凡是没显式写这两个键的部署，改后会去新位置开一个**空库** → 走"首次运行"
   建基线 → **忘掉已推过什么**（不报错、不补推），旧 PDF 也留在原地。所以这个变更的实质工作是
   **兼容探测**：新默认路径不存在、而仓库根 `data/state/cea_bot.db` 存在时，启动打一条响亮提示。
2. **`HOME` 缺失时 `~` 会字面化** —— `os.path.expanduser("~")` 在无 `HOME` 的环境下原样返回 `~`，
   于是程序会在 cwd 下建一个名叫 `~` 的目录。这与 README 已详述的"`D:\...` 在 Linux 上是合法的
   单层相对目录名"**属同一类**静默失效；默认值一旦改成用户目录，就必须加一条"解析结果必须是
   绝对路径，否则启动即报错"的守卫。
3. **PDF 归档要给 NapCat 读** —— 这是"同机交付"的硬前提。`~/.local/share`（将来若用 systemd 的
   `StateDirectory`，权限常为 0750）可能与 NapCat 的运行用户不同源。状态库进用户目录没问题，
   **PDF 归档是否跟着进，要在设计里单独判一次**。

### 时机

今天依赖这两个默认值的部署几乎为零（现有 `config.yaml` 与 README §8 的 `/srv` 方案都显式写了路径），
故现在改**近乎零迁移成本**；越晚做，上面第 1 条的兼容探测就越从"保险"变成"必需品"。

## 3. 栏目 2（学校发文）解析不出任何条目，配它必然每轮中止

**状态**：待处理，未开工 —— 2026-10-18 实测发现。
**触发条件**：把 `notice_type` 配成 `2`。

### 现状

`check_config` 允许 `notice_type ∈ {1, 2, 3}`（`src/cea_bot/config.py:45`，
报错文案还把 `2（学校发文）` 列为可选项），而解析层的行锚点是
`onclick="…open_tz('<edit_id>')…"`（`src/cea_bot/notices/parse.py:190`）。实测三个栏目首页：

| 栏目 | `open_tz` 出现次数 | 解析结果 |
|---|---|---|
| 1 校内通知 | 20 条数据行（另 1 处导航） | 20 条，正常 |
| 2 学校发文 | **0** | **0 条 → `NoticeParseError`，每轮中止** |
| 3 学术报告 | 20 条数据行（另 1 处导航） | 20 条，正常（但日期停在 2016-11/12，该栏目实际已停更） |

栏目 2 的数据行挂的是**附件直链**，根本没有详情页锚点：

```
<td class="listTableLine222"><a target="_blank" id="a_1"
    href="/defaultroot/public/download/download.jsp?verifyCode=…&FileName=…_last.pdf&name=…">
```

它的列结构也与栏目 1 不同：第一列日期、第二列**文号**（如"苏大人〔2026〕31号"）、
第三列文件名 —— 没有"发布单位"列。

### 影响

按 `notice_type: 2` 部署 = 每个定点都抛 `NoticeParseError`。这是**响亮失败**（不是静默失效），
但通知功能完全不可用，而配置校验把 `2` 说成合法值，从配置层面看不出任何问题。

### 打算怎么改（两条路，未定，先确认需求）

1. **支持它**：栏目 2 的行按"日期 + 文号 + 附件直链"解析；稳定标识恐怕得用 `FileName` / `verifyCode`
   而不是 `edit_id`；且它**没有详情页**，"推送正文从哪来"要另外定（可能只能推文号 + 附件）。
2. **收紧它**：`check_config` 只接受 `1`（或 `{1, 3}`），配 `2` 时启动即给出明确文案，
   指回本文件说明原因。

做之前先回答一个问题：**这个栏目到底要不要推？**

## 4. `_DATE` 没有左右边界，可能在更长的数字串中间命中

**状态**：待处理，未开工 —— 2026-10-18 在 `normalize-notice-date-digits` 的设计阶段发现，
并经裁定**刻意不在那次变更里修**（见该变更 design D3）。
**触发条件**：页面上出现形如 `12345-67-89` 的更长数字串。

### 现状

`src/cea_bot/notices/parse.py:197` 的 `_DATE` 用 `search` 且没有左右边界，因此 `12345-67-89`
会命中其中的 `2345-67-89`，被当成一条 2345 年的发布日期（`\d{4}` 从第 2 位起匹配）。

### 影响

日期取值错误 → PDF 名变成 `234567-…`、排序位置也跟着错。这是**既有行为**，与全角数字无关；
至今没有触发证据（2026-10-18 实测 60 条里没有这种串）。

### 为何不在 `normalize-notice-date-digits` 里顺手修

那次变更的目标是"把**已接受**的输入规范化"，而改边界属"改日期识别规则"，
会让变更面从"口径"扩到"识别"，且同样没有触发证据。
修法很直白（给 `_DATE` 加左右边界，例如 `(?<!\d)…(?!\d)`），等页面真的出现这种串、
或做日期识别专项时再处理。
